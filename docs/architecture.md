## State and command flow

**Local:** Board input in `src/scene/board-input.ts` sends intents through `checkers.ts` to `src/app/gameplay-actions.ts`. The action flow calls `GameController`, which applies `transitionSession` to its local session. `src/scene/dice.ts` samples and presents dice; the action flow passes values to the controller. An accepted move updates the game immediately, then the action flow asks the scene to animate it and releases the input lock on completion. Resize can finish an interrupted local presentation once; a late animation callback is ignored. Undo restores one saved pre-action `GameState` from the local session history.

**Online:** `src/app/match-session.ts` coordinates search, pairing, cancellation, and disconnect through transport and UI ports. `gameplay-actions.ts` passes the same user intentions to `GameController`, which routes them as `{type: 'roll' | 'move' | 'undo' | 'end' | 'restart'}` commands through `src/net/client.ts` to `/ws`. `src/net/lobby.ts` owns the authoritative session, checks the sender's seat and turn, and applies pure transitions. `server/index.ts` broadcasts state plus optional dice, move sequence, or reset hint. `src/app/online-game-flow.ts` receives updates, queues authoritative state while dice or checker animation plays, then asks the controller to adopt it. It calls scene and dice presentation through a small interface, without importing Three.js. Invalid packet shapes are ignored; valid-shaped but illegal or out-of-turn commands return the current state only to the sender.

`GameState` is the shared contract. It contains the board and off trays, phase, active player, original roll, unused dice, opening rolls, outcome, status message, and opening flag. `Update` adds `canUndo` because online clients do not own the server's history. Wire messages are JSON. MongoDB stores accounts, login sessions, and each live match as the two seat account ids plus the session document. Any game process can pair players from the shared queue and write a move if it still has the match's current revision. Each process keeps in memory only the matches of people connected to it, and learns about the opponent's moves from MongoDB. A disconnected seat is marked on the match. Any process ends that match 45 seconds later and records the player who stayed as the winner. A game that plays to a result keeps its final position and winner. The next game is a new document. There is no currency ledger.

The pure board rules live in `src/game/rules/`. `src/game/session/transition.ts` accepts one typed command and an immutable session input (`GameState` plus undo history), then returns a new session and semantic events or a rejection. It validates the phase, dice, legal move sequence, and intermediate landings. Events identify moves, fresh pins, bear-offs, roll outcomes, turn changes, and game results. `session/messages.ts` formats the existing status text from those events; Both `GameController` and the server apply the transition directly. `session/game.ts` remains as a compatibility facade for regression tests. `session/phase.ts` contains only authoritative turn phases. The controller owns pending roll and move presentation locks. `src/game/engine.ts` remains a compatibility entry point for older rule and test imports. The target Functional Core, Imperative Shell structure and its migration stages are in [the refactor plan](refactor-plan.md).

## Rendering and assets

`createStage` loads `Board.glb`, configures cameras, lights, postprocessing, and the render loop. `createGameplay` loads two checker models and creates 30 visual checker instances. `board-presentation.ts` maps logical positions to checker transforms, including pinned stacks, trays, and the opening deal. `board-input.ts` raycasts against 24 point targets and emits pickup, release, clear, and placement intents; the controller applies selection changes and `checkers.ts` emits accepted placement intents to `gameplay-actions.ts`. `src/ui/gameplay-hud.ts` renders the turn buttons, status, player panels, and held-checker choices, and emits control actions through `checkers.ts` to the action flow. `src/app/pickup-selection.ts` owns the held-checker queue, filters legal choices, and revalidates remaining selections after each accepted move. `src/game/pickup.ts` checks queue feasibility against the dice; each resulting move still passes through normal engine and online validation. `move-preview.ts` makes temporary visual copies for held checkers and the next hovered landing; these copies do not change game state. `move-animation.ts` owns checker interpolation and the pin impact. After a local animation completes, `gameplay-actions.ts` releases the controller input lock and revalidates held checkers; after an online animation, `online-game-flow.ts` adopts the pending server state. The landing ghost and halo render above destination highlights. A fresh pin moves slowly at first, accelerates into contact, zooms toward the landing point, then shakes and briefly brightens the canvas. This effect respects reduced-motion and motion preferences. `createDice` loads `Die.glb` and animates the result. `src/scene/layout.ts` changes presentation for portrait view without changing logical movement. Home, title, and waiting decorations are separate scene helpers. Runtime models live under `public/models`; `assets/source/build_assets.py` generates files under `assets/source/generated/` and does not overwrite runtime models.

## Development commands

Node.js 20.19+ or 22.12+ is required. Run `npm ci` once, then:

| Command                | Effect                                                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------------------------- |
| `npm run dev`          | Bundles the server, runs it on port 3001, and starts Vite on port 3000 with `/ws` proxied to 3001.         |
| `npm test`             | Discovers, bundles, and runs all `tests/*.test.ts` files.                                                  |
| `npm run test:browser` | Starts isolated web/game servers and checks local interaction plus authoritative two-seat rolls in Chrome. |
| `npm run build`        | Type-checks, builds the browser into `dist/`, and bundles the server into `dist-server/`.                  |
| `npm start`            | Serves `dist/` and `/ws` from one process on port 3000 or `PORT`.                                          |
| `npm run format:check` | Checks source formatting with Prettier.                                                                    |

The pure rules and session are the natural places to introduce a ruleset or mechanic state. Any online mechanic also needs a protocol representation, server validation, and client presentation. Keep random decisions and effect resolution explicit in shared state so the UI can display them and both clients stay synchronized. Add tests at the rules, session, and lobby boundaries before visual polish. The browser smoke runner uses the system Chrome/Chromium through `playwright-core`; `PLAKOTO_CHROME_PATH` overrides executable discovery.
