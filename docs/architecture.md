## State and command flow

**Local:** Board input in `src/scene/board-input.ts` sends intents through `checkers.ts` to `src/app/gameplay-actions.ts`. The action flow calls `GameController`, which applies `transitionSession` to its local session. The controller's local authority samples the result and stores it in its typed roll operation, then `src/scene/dice.ts` presents those forced values before the action flow returns them to the transition. An accepted move updates the game immediately, then the action flow asks the scene to animate it and releases the matching move operation on completion. Resize can finish an interrupted local presentation once; a late animation callback is ignored and cannot release a newer operation. Undo restores one saved pre-action `GameState` from the local session history.

**Online:** `src/app/match-session.ts` coordinates search, pairing, cancellation, rematch messaging, and disconnect through transport and UI ports. `src/net/client.ts` opens `/ws`, sends `{type: 'hello', protocol}` first, and accepts gameplay traffic only after `ready`/`resume`; incompatible or unauthenticated clients receive a typed rejection. `gameplay-actions.ts` passes the same user intentions to `GameController`, which routes them as `{type: 'roll' | 'move' | 'undo' | 'end' | 'restart' | 'forfeit' | 'pickAbility' | 'playAbility'}` commands; `end` may carry one validated `WITH_END_TURN` activation, while `playAbility` covers the post-roll window. `src/net/lobby.ts` owns the authoritative session, separates matchmaking queues by ruleset/config hash, checks the sender's seat and turn, samples draft, Recast, and passive dice randomness, and applies pure transitions. `server/index.ts` broadcasts state plus optional movement dice, a Recast die index, move sequence, or reset hint; draft order attempts already live in the authoritative state and are not duplicated in the update envelope. `src/app/online-game-flow.ts` receives updates, queues authoritative state while dice or checker animation plays, then asks the controller to adopt it. It calls scene and dice presentation through a small interface, without importing Three.js. Malformed packet shapes return `INVALID_COMMAND`; valid-shaped but illegal, out-of-turn, stale, or finished-match commands return a typed error code to the sender. Resigning ends the session with the opponent as winner, and the server keeps a finished match in place until both players accept a rematch.

`GameState` is the shared contract. It contains the board and off trays, phase, active player, physical roll, roll source, unused movement tokens, public dice modifiers, opening rolls, outcome, status message, opening flag, ruleset, variant-config hash, and nullable powerup state. Classic state uses `CLASSIC`, a null hash/source, no modifiers, and null powerup state. A powerup session tracks completed rounds, public loadouts, effects, passive counters, config-resolved passive policy snapshots, turn usage, and a discriminated draft state. `Update` adds `canUndo` because online clients do not own the server's history and may include the same authoritative `SessionEvent[]` used by local transitions. Wire messages are JSON. MongoDB stores accounts, login sessions, profile-separated queue entries, and each match as the two seat account ids, complete session document, immutable resolved variant-configuration snapshot, connection flags, and the latest accepted revision's event/presentation envelope. The envelope omits state and undo history; the server combines it with the stored session to reproduce dice, reroll, and move presentation. Stored sessions are structurally validated before resume: phase, 24-point board, two off trays, exactly 30 unique checker ids, dice ranges, outcome shape, ruleset, and configuration hash must all agree. One game server owns live authority for a database. On startup it clears volatile queue rows and marks every live match away, then restores matches as players reconnect. A paired seat that has connected before gets a 45-second reconnect grace; a seat that never connected gets 20 seconds. Forfeit, disconnect, no-show, cancellation, and normal completion persist a typed `Outcome.kind`, final position, and winner. A finished game remains the active match until both players accept a rematch, which starts a new document with the same rules context. There is no currency ledger.

The pure board rules live in `src/game/rules/`. `src/game/session/transition.ts` accepts one typed command and an immutable session input (`GameState` plus undo history), then returns a new session and semantic events or a rejection. It validates the phase, dice, legal move sequence, and intermediate landings. Events identify moves, fresh pins, bear-offs, roll outcomes, turn changes, and game results. `session/messages.ts` formats the existing status text from those events; Both `GameController` and the server apply the transition directly. `session/game.ts` remains as a compatibility facade for regression tests. `session/phase.ts` contains only authoritative turn phases. The controller uses one discriminated operation state for roll, move, draft-pick, end-turn, ability, and remote-move workflows while keeping ability targeting separate. Its online authority helper records the operation before sending the command; authoritative adoption cancels the operation and advances the epoch. `src/game/engine.ts` remains a compatibility entry point for older rule and test imports. The target Functional Core, Imperative Shell structure and its migration stages are in [the refactor plan](refactor-plan.md).

## Rendering and assets

`createStage` loads `Board.glb`, configures cameras, lights, postprocessing, and the render loop. `createGameplay` loads two checker models and creates 30 visual checker instances. `board-presentation.ts` maps logical positions to checker transforms, including pinned stacks, trays, and the opening deal. `board-input.ts` raycasts against 24 point targets and emits pickup, release, clear, and placement intents; the controller applies selection changes and `checkers.ts` emits accepted placement intents to `gameplay-actions.ts`. `src/ui/gameplay-hud.ts` renders the turn buttons, status, player panels, and held-checker choices, and emits control actions through `checkers.ts` to the action flow. It composes the thin `src/ui/draft-panel.ts` boundary over `src/ui/abilities`: `draft-dialog.ts` owns modal draft and order reveal, `card-content.ts` supplies reusable configured card content, `loadout-stack.ts` owns overlapping inventories, `focused-ability-card.ts` owns details and Use interaction, and `active-effect-list.ts` formats public effects. `presenters.ts` is the complete ability-ID UI registry for counter copy, roll prompts, option labels, and direct-die hints; it formats controller-provided legal choices without deciding legality. `src/app/pickup-selection.ts` owns the held-checker queue, filters legal choices, and revalidates remaining selections after each accepted move. `src/game/pickup.ts` checks queue feasibility against the dice; each resulting move still passes through normal engine and online validation. `move-preview.ts` makes temporary visual copies for held checkers and the next hovered landing; these copies do not change game state. `move-animation.ts` owns checker interpolation and the pin impact. Intermediate combined-move landings remain visible and rules-validating, but only a pin on the final landing receives the slow-motion impact. After a local animation completes, `gameplay-actions.ts` releases the controller input lock and revalidates held checkers; after an online animation, `online-game-flow.ts` adopts the pending server state. The landing ghost and halo render above destination highlights. A final fresh pin moves slowly at first, accelerates into contact, zooms toward the landing point, then shakes and briefly brightens the canvas. This effect respects reduced-motion and motion preferences. `createDice` loads `Die.glb`, animates results, positions accessible HTML hit targets over Recast-eligible dice, and can throw a single authority-identified die while leaving its partner still. `src/scene/layout.ts` changes presentation for portrait view without changing logical movement. Home, title, and waiting decorations are separate scene helpers. Runtime models live under `public/models`; `assets/source/build_assets.py` generates files under `assets/source/generated/` and does not overwrite runtime models.

The ability draft UI presents the final decisive authoritative order attempt once, with one player-colored animated CSS die per avatar; these dice never feed movement or choose an outcome. Authority still records and resolves ties, but the dialog does not replay those internal attempts. Once the reveal finishes, the current picker's avatar remains next to the dialog. The shared bottom inventory slot shows only the active player's overlapping, focusable card stack; it sits immediately right of the Roll control on landscape screens and above the controls when portrait width is constrained. A turn change slides the outgoing tray toward its player side and the incoming tray in from the other side. It remains separate from the player avatar panels and retains a distinct explicit Use action. `src/scene/ability-effects.ts` derives temporary Frost Seal and Bastion board aids from public effect state; the translucent ice, ghost checker, and icons are non-interactive presentation and do not participate in rule evaluation or picking.

## Development commands

Node.js 20.19+ or 22.12+ is required. Run `npm ci` once, then:

| Command                | Effect                                                                                                                                   |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `npm run dev`          | Bundles the server, runs it on port 3001, and starts Vite on port 3000 with `/ws` proxied to 3001.                                       |
| `npm test`             | Discovers, bundles, and runs all `tests/*.test.ts` files.                                                                                |
| `npm run test:browser` | Starts isolated web/game servers and checks local interaction plus authoritative two-seat drafts, activation, and replacement in Chrome. |
| `npm run build`        | Type-checks, builds the browser into `dist/`, and bundles the server into `dist-server/`.                                                |
| `npm start`            | Serves `dist/` and `/ws` from one process on port 3000 or `PORT`.                                                                        |
| `npm run format:check` | Checks source formatting with Prettier.                                                                                                  |

The pure rules and session are the natural places to introduce a ruleset or mechanic state. Any online mechanic also needs a protocol representation, server validation, and client presentation. Keep random decisions and effect resolution explicit in shared state so the UI can display them and both clients stay synchronized. Add tests at the rules, session, and lobby boundaries before visual polish. The browser smoke runner uses the system Chrome/Chromium through `playwright-core`; `PLAKOTO_CHROME_PATH` overrides executable discovery. Its injected client selects the registered one-round `fast-balance` profile so two real drafts, activation, and replacement are covered without changing the public `powerups-v1` selection. The runner also supplies the environment-only `PLAKOTO_TEST_RANDOM_SEED` to the server authority so Recast is offered deterministically; normal servers do not set it, clients cannot provide it, and production randomness remains backed by `node:crypto`.

`src/ui/shell.ts` exposes Classic and Powerups selections, derives help text from the resolved definitions, and sends one typed `MatchSelection` to local setup or matchmaking. The waiting screen and gameplay HUD show the selected profile. `rules-context.ts` is the shared selection, queue-key, snapshot, and state-validation boundary used by local setup, matchmaking, legacy restore, and online join; unknown profiles and mismatched snapshots are rejected. `src/game/variant/config` validates and deeply freezes complete profiles and assigns deterministic hashes. `abilities/registry.ts` is the only ability-ID metadata registry and `abilities/` owns shared definition and active-ability capability infrastructure; concrete definitions remain separated into `powerups/definitions` and `passives/definitions`. Each definition owns its config validation, config-derived display copy, and rule behavior. Frost Seal, Bastion, and Jinx colocate their pure end-turn targeting, effect construction, and effect-validity capabilities; Clear Skies colocates its before-roll targeting and effect-removal capability; Recast, Nudge, and Opportunist colocate their after-roll options, authority-randomness requirements, application, and resource hooks. `abilities/behavior-registry.ts` aggregates those timing capabilities and preserves ID/config type correlation. `passives/capabilities.ts` defines passive roll, movement, inventory, powerup-use, counter, and lifecycle hooks; `passives/behavior-registry.ts` composes the hooks exported beside Loaded Knuckles, Quartermaster, Home Guard, and Opportunist. `passives/policy.ts` is a compatibility facade over that registry rather than an ability-specific switchboard. `abilities/roll-adjustment.ts` shares bounded numeric-die option and application logic between Nudge and Opportunist. `transitionSession` receives an explicit immutable rules context, counts configured rounds, owns draft phase transitions, and applies powers through timing-specific pure commands. `activation.ts`, `powerups/before-roll.ts`, and `roll-activation.ts` coordinate timing, inventory/resource consumption, and public state without owning concrete ability rules. `powerups/roll-effects.ts` resolves delayed Jinx effects against effective movement tokens while preserving physical dice and recording public modifiers. `move-policy.ts` composes public passive policies with active-effect and token restrictions after baseline Plakoto generates candidate landings. Local play and the online authority use the same boundaries; the server supplies draft, Recast, and passive-roll randomness and rejects stale instances, unearned Focus, or illegal targets.

The staged follow-up work for persistence, typed ability behavior capabilities, controller workflow state, and reusable ability UI is tracked in [the variant implementation improvement plan](variant-implementation-improvements.md).

In development, `src/game/random.ts` supplies a stable seeded `RandomInt` for explicit local playtest seeds. The seed field is blank by default, so ordinary development games retain the cryptographic source just like production local games; online games always retain server-owned randomness. `src/app/playtest-report.ts` subscribes to accepted controller events and stores only an in-memory, schema-versioned report. Each entry pairs semantic events with a compact public state snapshot so effect duration, offers, inventory, rolls, stalls, and outcomes can be analyzed without scraping UI copy. `src/app/playtest-analysis.ts` validates imported schema-one reports, groups them by ruleset/profile/configuration hash, and derives offer/pick/replacement/use, hold-duration, stall, game-length, and winner correlations. Unfinished observations remain explicitly censored. The shell can download both raw and aggregate JSON in development; neither path has a network sink. The development profile selector resolves only IDs in the normal closed registry and never changes online authority.
