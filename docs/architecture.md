## State and command flow

**Local:** Board input in `src/scene/board-input.ts` sends intents through `checkers.ts` to `src/app/gameplay-actions.ts`. The action flow calls `GameController`, which applies `transitionSession` to its local session. The controller's local authority samples the result, then `src/scene/dice.ts` presents those forced values before the action flow returns them to the transition. An accepted move updates the game immediately, then the action flow asks the scene to animate it and releases the input lock on completion. Resize can finish an interrupted local presentation once; a late animation callback is ignored. Undo restores one saved pre-action `GameState` from the local session history.

**Online:** `src/app/match-session.ts` coordinates search, pairing, cancellation, and disconnect through transport and UI ports. `gameplay-actions.ts` passes the same user intentions to `GameController`, which routes them as `{type: 'roll' | 'move' | 'undo' | 'end' | 'restart' | 'pickAbility' | 'playAbility'}` commands through `src/net/client.ts` to `/ws`; `end` may carry one validated `WITH_END_TURN` activation, while `playAbility` covers the post-roll window. `src/net/lobby.ts` owns the authoritative session, separates matchmaking queues by ruleset/config hash, checks the sender's seat and turn, samples draft, Recast, and passive dice randomness, and applies pure transitions. `server/index.ts` broadcasts state plus optional dice, a Recast die index, draft rolls, move sequence, or reset hint. `src/app/online-game-flow.ts` receives updates, queues authoritative state while dice or checker animation plays, then asks the controller to adopt it. It calls scene and dice presentation through a small interface, without importing Three.js. Invalid packet shapes are ignored; valid-shaped but illegal or out-of-turn commands return the current state only to the sender.

`GameState` is the shared contract. It contains the board and off trays, phase, active player, physical roll, roll source, unused movement tokens, public dice modifiers, opening rolls, outcome, status message, opening flag, ruleset, variant-config hash, and nullable powerup state. Classic state uses `CLASSIC`, a null hash/source, no modifiers, and null powerup state. A powerup session tracks completed rounds, public loadouts, effects, passive counters, config-resolved passive policy snapshots, turn usage, and a discriminated draft state. `Update` adds `canUndo` because online clients do not own the server's history and may include the same authoritative `SessionEvent[]` used by local transitions. Wire messages are JSON. MongoDB stores accounts, login sessions, profile-separated queue entries, and each live match as the two seat account ids plus the complete session document. Any game process can pair players with the same ruleset/configuration and write a move if it still has the match's current revision. Each process keeps in memory only the matches of people connected to it and learns about the opponent's moves from MongoDB. A disconnected seat is marked on the match. Any process ends that match 45 seconds later and records the player who stayed as the winner. A game that plays to a result keeps its final position and winner. The next game is a new document using the same rules context. There is no currency ledger.

The pure board rules live in `src/game/rules/`. `src/game/session/transition.ts` accepts one typed command and an immutable session input (`GameState` plus undo history), then returns a new session and semantic events or a rejection. It validates the phase, dice, legal move sequence, and intermediate landings. Events identify moves, fresh pins, bear-offs, roll outcomes, turn changes, and game results. `session/messages.ts` formats the existing status text from those events; Both `GameController` and the server apply the transition directly. `session/game.ts` remains as a compatibility facade for regression tests. `session/phase.ts` contains only authoritative turn phases. The controller owns pending roll and move presentation locks. `src/game/engine.ts` remains a compatibility entry point for older rule and test imports. The target Functional Core, Imperative Shell structure and its migration stages are in [the refactor plan](refactor-plan.md).

## Rendering and assets

`createStage` loads `Board.glb`, configures cameras, lights, postprocessing, and the render loop. `createGameplay` loads two checker models and creates 30 visual checker instances. `board-presentation.ts` maps logical positions to checker transforms, including pinned stacks, trays, and the opening deal. `board-input.ts` raycasts against 24 point targets and emits pickup, release, clear, and placement intents; the controller applies selection changes and `checkers.ts` emits accepted placement intents to `gameplay-actions.ts`. `src/ui/gameplay-hud.ts` renders the turn buttons, status, player panels, and held-checker choices, and emits control actions through `checkers.ts` to the action flow. It composes `src/ui/draft-panel.ts`, which renders config-derived draft cards, overlapping inventory cards, focus details, and same-kind replacement choices without deciding pick legality. `src/app/pickup-selection.ts` owns the held-checker queue, filters legal choices, and revalidates remaining selections after each accepted move. `src/game/pickup.ts` checks queue feasibility against the dice; each resulting move still passes through normal engine and online validation. `move-preview.ts` makes temporary visual copies for held checkers and the next hovered landing; these copies do not change game state. `move-animation.ts` owns checker interpolation and the pin impact. Intermediate combined-move landings remain visible and rules-validating, but only a pin on the final landing receives the slow-motion impact. After a local animation completes, `gameplay-actions.ts` releases the controller input lock and revalidates held checkers; after an online animation, `online-game-flow.ts` adopts the pending server state. The landing ghost and halo render above destination highlights. A final fresh pin moves slowly at first, accelerates into contact, zooms toward the landing point, then shakes and briefly brightens the canvas. This effect respects reduced-motion and motion preferences. `createDice` loads `Die.glb`, animates results, positions accessible HTML hit targets over Recast-eligible dice, and can throw a single authority-identified die while leaving its partner still. `src/scene/layout.ts` changes presentation for portrait view without changing logical movement. Home, title, and waiting decorations are separate scene helpers. Runtime models live under `public/models`; `assets/source/build_assets.py` generates files under `assets/source/generated/` and does not overwrite runtime models.

The ability draft UI presents the final decisive authoritative order attempt once, with one player-colored animated CSS die per avatar; these dice never feed movement or choose an outcome. Authority still records and resolves ties, but the dialog does not replay those internal attempts. Once the reveal finishes, the current picker's avatar remains next to the dialog. Each player inventory is an overlapping, focusable card stack with a separate explicit Use action. `src/scene/ability-effects.ts` derives temporary Frost Seal and Bastion board aids from public effect state; the translucent ice, ghost checker, and icons are non-interactive presentation and do not participate in rule evaluation or picking.

## Development commands

Node.js 20.19+ or 22.12+ is required. Run `npm ci` once, then:

| Command                | Effect                                                                                                                                   |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `npm run dev`          | Bundles the server, runs it on port 3001, and starts Vite on port 3000 with `/ws` proxied to 3001.                                       |
| `npm test`             | Discovers, bundles, and runs all `tests/*.test.ts` files.                                                                                |
| `npm run test:browser` | Starts isolated web/game servers and checks local interaction plus authoritative two-seat drafts, activation, and replacement in Chrome. |
| `npm run build`        | Type-checks, builds the browser into `dist/`, and bundles the server into `dist-server/`.                                                |
| `npm start`            | Serves `dist/` and `/ws` from one process on port 3000 or `PORT`.                                                                        |
| `npm run format:check` | Checks source formatting with Prettier.                                                                                                  |

The pure rules and session are the natural places to introduce a ruleset or mechanic state. Any online mechanic also needs a protocol representation, server validation, and client presentation. Keep random decisions and effect resolution explicit in shared state so the UI can display them and both clients stay synchronized. Add tests at the rules, session, and lobby boundaries before visual polish. The browser smoke runner uses the system Chrome/Chromium through `playwright-core`; `PLAKOTO_CHROME_PATH` overrides executable discovery. Its injected client selects the registered one-round `fast-balance` profile so two real drafts, activation, and replacement are covered without changing the public `powerups-v1` selection. The runner also supplies the environment-only `PLAKOTO_TEST_RANDOM_SEED` to the server authority so Recast is offered deterministically; normal servers do not set it, clients cannot provide it, and production randomness remains backed by `node:crypto`.

`src/ui/shell.ts` exposes Classic and Powerups selections, derives help text from the resolved definitions, and sends one typed `MatchSelection` to local setup or matchmaking. The waiting screen and gameplay HUD show the selected profile. `match-session.ts` and the server resolve the requested ID through the same closed profile registry; unknown profiles are rejected and each resolved configuration hash has its own online queue. `src/game/variant/config` validates and deeply freezes complete profiles and assigns deterministic hashes. `abilities/registry.ts` is the only ability-ID registry and `abilities/` retains only shared definition infrastructure; concrete definitions are separated into `powerups/definitions` and `passives/definitions`. Each definition owns its config validation and config-derived display copy. `transitionSession` receives an explicit immutable rules context, counts configured rounds, owns draft phase transitions, and applies powers through timing-specific pure commands. `activation.ts` is the central handler map for end-turn targeting, consumption, public effect creation, and boundary expiry. `powerups/before-roll.ts` derives first-class public effect targets and resolves Clear Skies removals atomically. `powerups/roll-effects.ts` resolves delayed Jinx effects against effective movement tokens while preserving physical dice and recording public modifiers. `roll-activation.ts` derives legal die choices for expendable powers and Focus-backed passive actions, then applies authority-provided results without sampling randomness itself. `passives/policy.ts` centralizes equipped-passive queries, config-resolved policy snapshots, derived inventory capacity, cooldown/Focus accounting, Loaded Knuckles roll generation, Home Guard movement restrictions, and double-token counts. `move-policy.ts` composes those passive policies with public active-effect and token restrictions after baseline Plakoto generates candidate landings. Local play and the online authority use the same boundaries; the server supplies draft, Recast, and passive-roll randomness and rejects stale instances, unearned Focus, or illegal targets.

In development, `src/game/random.ts` supplies a stable seeded `RandomInt` for explicit local playtest seeds. The seed field is blank by default, so ordinary development games retain the cryptographic source just like production local games; online games always retain server-owned randomness. `src/app/playtest-report.ts` subscribes to accepted controller events and stores only an in-memory, schema-versioned report. Each entry pairs semantic events with a compact public state snapshot so effect duration, offers, inventory, rolls, stalls, and outcomes can be analyzed without scraping UI copy. `src/app/playtest-analysis.ts` validates imported schema-one reports, groups them by ruleset/profile/configuration hash, and derives offer/pick/replacement/use, hold-duration, stall, game-length, and winner correlations. Unfinished observations remain explicitly censored. The shell can download both raw and aggregate JSON in development; neither path has a network sink. The development profile selector resolves only IDs in the normal closed registry and never changes online authority.
