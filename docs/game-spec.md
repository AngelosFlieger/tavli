# Game specification: implemented baseline

This document describes the current code, not every possible Plakoto rule. The game is a single two-player Plakoto game with local play on one device or an online match. The title screen offers the unchanged `CLASSIC` ruleset and the configurable `POWERUPS_V1` ruleset; the choice is fixed for that game.

## Board and players

| Item        | Current behavior                                                                                                                             |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Players     | Player 0 is crimson and player 1 is ivory. Each owns 15 checkers.                                                                            |
| Checker IDs | `0–14` are crimson; `15–29` are ivory. IDs are stable through moves and animation.                                                           |
| Points      | The board has 24 physical points, numbered `0–23`. `board[point]` stores checker IDs from bottom to top; `off[player]` stores borne-off IDs. |
| Start       | All crimson checkers start on point `0`; all ivory checkers start on point `12`.                                                             |
| Movement    | Crimson follows `0 → 1 → … → 11 → 23 → 22 → … → 12`. Ivory follows `12 → 13 → … → 23 → 11 → 10 → … → 0`. The paths are exact reversals.      |
| Home        | Crimson's final six points are `17, 16, 15, 14, 13, 12`; ivory's are `5, 4, 3, 2, 1, 0`.                                                     |

`src/game/points.ts` is the source of truth for physical point IDs and paths. Portrait layout stretches the rendered board but retains the same point IDs and rules.

## Starting and taking turns

1. Player 1 (crimson) rolls two dice, then Player 2 (ivory) rolls two dice. The higher **sum** starts. Equal sums make both players roll again in the same order.
2. The starter rolls a fresh pair for the first actual turn. Later turns alternate.
3. Two different dice give one movement per die. Doubles give four movements of that value.
4. The player must use the maximum number of available movements possible from the current position. If either of two different dice could be used but both cannot, the higher die is required. If only the lower die is playable, it may be used. Winning moves can end play immediately.
5. A checker can consume several dice in one selected action if each intermediate landing is legal. This includes two to four steps with doubles. One Undo reverses that whole selected action. An enemy singleton crossed on an intermediate hop participates in legality, but the pin slow-motion presentation runs only when the selected action finishes on that singleton and leaves it pinned.
6. After all required movements have been made, or when none are legal, the turn enters `TURN_COMPLETE`. The player presses **End Turn** to hand play to the opponent. Undo remains available for actions already made in that turn.

During a turn, players may pick up multiple checkers before placing any. The local pickup queue is ordered: the first checker picked up is placed first, and remaining checkers stay in hand. A regular roll can hold at most two, while doubles can hold at most four. A checker can be added only if the queued checkers can each make a legal placement in that order with the remaining dice. Destinations for the first checker are filtered to preserve those later placements. Clicking the same source again picks up the next checker in its stack when legal. **Put back last** removes the latest pickup; Escape clears the queue. Shift-click gives pickup priority when a point is both a source and a destination. The queue is presentation state and is not sent to the server; each placed move remains server-validated.

The authoritative `GameState.phase` values are `OPENING_ROLL`, `WAITING_FOR_ROLL`, `WAITING_FOR_MOVE`, `TURN_COMPLETE`, and `GAME_OVER`. A roll or move resolves to its resulting phase as soon as the command is accepted. The application controller temporarily locks input while local dice or checker animation plays, or while an online result is pending; these waits are not part of shared game state.

## Landing, pinning, and bearing off

- A checker may land on an empty point, a point controlled by its own player, or a point occupied by exactly one opposing checker. Landing on that lone enemy **pins** it underneath; no checker is hit or sent to a bar.
- The top checker controls a point. A pinned checker cannot move, and its owner cannot land on that point while the opponent controls it. Multiple friendly checkers can sit above a pinned checker; the pin ends when the last controlling checker leaves.
- A player may bear off only when all of their remaining board checkers are on their six home points and none of their checkers is pinned.
- A die bears off a checker exactly its distance from the exit. A larger die may bear off only a checker on the highest occupied point, meaning the one farthest from the exit among that player's remaining checkers. Moving within home is also allowed when legal.
- A bear-off move uses destination `-1` in the engine and wire protocol.

## End of game

| Result         | Condition                                                                                                                                   | `Outcome.points` |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------: |
| Normal win     | A player bears off all 15 and the opponent has borne off at least one.                                                                      |                1 |
| Mars           | A player bears off all 15 and the opponent has borne off none.                                                                              |                2 |
| Mother victory | A player pins the opponent's sole checker on the opponent's starting point, and the winner has no checker left on their own starting point. |                2 |
| Draw           | Both players' mothers are pinned. This check precedes individual wins.                                                                      |                0 |

The result stores a winner (`null` for a draw), points, and a reason string. The UI shows the winner and reason; points are **not** displayed or added to a match score. New game resets to the opening setup.

## Local and online behavior

- Local play is two people sharing one device. One browser authority samples dice and variant randomness with `crypto.getRandomValues`, records the selected values, and forces the visible dice to settle on that result. Development builds can replace this authority source with an explicitly seeded reproducible generator for a local balance playtest.
- Online play requires an account. The WebSocket begins with a versioned `hello` handshake; incompatible clients receive an explicit rejection. The oldest waiting account with the same ruleset and balance profile is paired with the next. The first joined player gets crimson and the first opening roll. The server chooses movement dice, draft order/offers, rerolls, and passive randomness, validates commands and move sequences, and sends the resulting state to both clients. A client can act only for its assigned player on that player's turn. Each match stores its complete resolved balance configuration, so an in-progress game and its rematch keep the same rules even if the registered profile is tuned later. The latest accepted revision also stores its semantic events and presentation metadata.
- The online server is the single authority for live matches. On startup it clears volatile queue rows and places every stored live match into a reconnect grace. A seat that has connected before may resume for 45 seconds; a paired account that never connects loses after 20 seconds. A player can also open a private room that yields a six-character invite code; another account entering that code is paired directly into a normal match. Online matches use a server-owned clock configured once per process: a 30-second opening roll, a 2-minute turn, and a 15-second bank by default. Drafts and disconnects pause the clock; the active seat loses on expiry with a `TIMEOUT` result. Disconnects, no-shows, resignations, timeouts, cancellations, mother wins, mars, bear-offs, and draws store a typed result kind and final position. A finished match can be restarted only after both players accept the rematch. Signing out or cancelling ends the match and releases both accounts. Invalid commands return a typed error code rather than silently doing nothing.
- Motion, texture, sound, language, and match-history preferences persist in local storage; the interface is available in English and Greek. The account session is an HttpOnly cookie. Email and username are unique. Online game state is stored in MongoDB; local games, on-device match history, and balance reports remain on the device and are not saved by the server.

## Powerups ruleset

Selecting Powerups starts the validated `powerups-v1` profile. Local play uses that same resolved profile as online authority; online matchmaking separates queues by ruleset and configuration hash. The current profile opens a public three-card draft after every three completed rounds. Dice decide first pick, ties reroll, the first player takes one card, and the other player chooses from the remaining two. Inventories, effects, counters, draft rolls, and the exact profile hash are public state. A player normally holds two expendable powers and one passive and may use one expendable power per own turn; all of those values come from the profile rather than UI or rule constants.

The authority may reroll a tied draft order internally, but the draft UI presents only the final decisive attempt once when the dialog opens, with one animated die in each player's color. Both avatars begin beside the dice, then only the current picker's avatar remains beside the card choices. The textual status is deliberately generic and remains available for accessibility. Each player's public inventory is an overlapping card stack. Selecting a card opens its complete configured description and a separate **Use** action when that card is legal in the current timing window; passive cards that have no manual action say that they are always active.

Frost Seal and Bastion can be selected from inventory at `TURN_COMPLETE`, targeted on highlighted legal points, and submitted atomically with End Turn. Jinx is also played with End Turn, automatically targets the opponent, and creates a public delayed effect. On the opponent's next eligible movement roll it reduces the configured effective movement token while preserving the physical dice; it is then consumed. Its penalty, floor, high/low selection, double behavior, and draft-boundary expiry are configured in the match profile. Before rolling, Clear Skies can select a public hostile effect and atomically remove it plus additional eligible effects up to its configured maximum. Removable tags and permission to remove opponent protection are profile-controlled; without a legal effect it cannot be played. Recast and Nudge can be used after a movement roll and before the first checker moves. After Recast's **Use** action, its legal physical dice receive direct click targets. The clicked die index is validated by the authority, only that die is visibly thrown again on both clients, and the other die remains stationary. The result changes the corresponding physical die and movement token and preserves the original movement count unless configured otherwise. Nudge changes a movement token while keeping the physical roll visible and records the before/after values.

Public effects also have temporary presentation aids for playtesting. Frost Seal surrounds its controlled checker with translucent ice and a snow marker. Bastion shows a translucent copy of its anchored checker in front of the stack with a shield marker. Hostile player effects add a visible treatment to the affected player card, while the existing effect label remains the text alternative. These visuals are derived solely from authoritative state and do not participate in targeting or rules.

Loaded Knuckles makes the first movement die fair, applies its exact configured match probability to the second, samples a non-match uniformly from the other faces, and reduces doubles to its configured movement-token count. The local controller forces the visible dice to that result; online matches generate it on the server. `rollSource` records that the passive supplied the distribution. Quartermaster derives extra inventory capacity from its config and starts a public own-turn cooldown whenever its owner consumes a powerup. During that cooldown, all powerup activation windows are unavailable. Replacing Quartermaster clears its counter; cards occupying its former extra slots remain until used or replaced rather than being discarded automatically. Home Guard prevents configured pins against the owner's home singletons and prevents the owner from pinning in the opponent's home; its two sides and start-point exclusion are independently configurable and represented by public passive-policy state. Opportunist grants public Focus when the opponent's initial movement roll has no legal move. Its owner can spend Focus after a later roll to apply a configured dice adjustment without consuming the passive or a powerup use; its lower inventory capacity is derived while equipped. All ten initial cards are server-validated and publicly represented in state. [The powerups implementation plan](powerups-plan.md) and [proposed ability catalog](ability-catalog.md) record the version-one design and current implementation direction; the Classic baseline above remains unchanged.

In a development build, local play additionally exposes the registered profile and an optional unsigned 32-bit seed. A blank seed keeps the normal cryptographic source and produces fresh randomness for each new game. An explicit seed switches to the reproducible generator and drives gameplay dice, offers, order rolls, passive probability checks, and ability rerolls through the same local authority seam. Settings can download a schema-versioned JSON playtest report containing the exact profile/hash/seed, authoritative semantic events, public loadout/effect snapshots, and summary counts for explicitly seeded runs. Multiple reports can be imported for local aggregation; invalid files are rejected, distinct configuration hashes remain separate, and incomplete games/held cards are marked as censored instead of being counted as losses or zero-duration holds. The aggregate JSON includes offer, pick, replacement, use, expiry, hold-duration, stall, game-length, opening-winner, and draft-first correlations. Reports stay in browser memory and are never uploaded. Online play continues to use unpredictable server-owned randomness; accepting a client seed online would reveal future outcomes and is intentionally unsupported.

Before implementing another mechanic, specify its trigger and timing, targets, effect and duration, stacking rules, interaction with pinning/bearing off/wins, whether it can be undone, and how it appears in both local and online state. Online random outcomes must be selected by the server. The Classic baseline above remains playable and testable as a distinct ruleset. [The variant implementation improvement plan](variant-implementation-improvements.md) records the staged persistence, behavior-registry, controller, and UI work that follows the initial implementation.

## Temporary water-effect preview

The in-game **Test Water** control previews stylized water flowing across the board. It has no gameplay effect: it does not move or pin checkers, consume dice, advance turns, use ability inventory, or send multiplayer commands. Each client sees only its own preview. Reduced-motion preferences are respected. No water powerup has been added to any ruleset.
